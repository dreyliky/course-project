# Звіт з лабораторної роботи 6. TypeScript і Vite

**Репозиторій:** https://github.com/dreyliky/course-project
**Опубліковані сторінки:** https://dreyliky.github.io/course-project/

## 1. Мета роботи

Перевести клієнтську частину проєкту на TypeScript, налаштувати збірку та
інструменти контролю якості коду.

## 2. Що зроблено

Проєкт із набору статичних файлів став проєктом зі збіркою: Vite у
багатосторінковому режимі, TypeScript у строгому режимі, описані типи
предметної області, ESLint із правилами на основі типів і Prettier. Публікація
переїхала з «гілка main, корінь» на GitHub Actions, бо тепер у мережу має
потрапляти результат збірки, а не вихідний код.

## 3. Структура після міграції

```
src/
├── scripts/   # клієнтська логіка: api, commits, dom, format, main, modal, theme
├── styles/    # tokens.css і style.css
└── types/     # типи предметної області: commit, state, theme
```

HTML-сторінки лишилися в корені: Vite розглядає їх як точки входу й шукає саме
там. Стилі й скрипти переїхали з `assets/` у `src/`, бо тепер це не готові до
віддачі файли, а вихідний код, який проходить через збірку.

## 4. Збірка Vite

Проєкт багатосторінковий, тому кожна сторінка оголошена окремою точкою входу:

```ts
rollupOptions: {
    input: {
        index: page('index'),
        about: page('about'),
        activity: page('activity'),
        contact: page('contact')
    }
}
```

Без цього Vite зібрав би лише `index.html`, а решта сторінок просто не
потрапила б у `dist/`.

Окремо задано `base: '/course-project/'`. Сайт лежить не в корені домену, а в
підкаталозі, і без цього параметра зібрані сторінки шукали б стилі за адресою
`/assets/...` замість `/course-project/assets/...`.

Результат збірки: чотири сторінки, один файл стилів і один файл скриптів,
разом близько 15 кБ, із них 4,7 кБ після стиснення. Імена файлів містять хеш
вмісту, тому кеш браузера оновлюється сам при зміні коду.

## 5. Строгий режим TypeScript

У `tsconfig.json` увімкнено `strict`, а додатково:

| Параметр | Що ловить |
| --- | --- |
| `noUncheckedIndexedAccess` | звернення за індексом повертає `T \| undefined`, бо масив може бути коротшим |
| `exactOptionalPropertyTypes` | розрізняє «поля немає» і «поле дорівнює undefined» |
| `noImplicitReturns` | гілку функції, з якої забули повернути значення |
| `noUnusedLocals`, `noUnusedParameters` | залишки після правок |
| `verbatimModuleSyntax` | змушує писати `import type` там, де імпортується лише тип |

Найбільше змін вимагав `noUncheckedIndexedAccess`. Код `message.split('\n')[0]`
раніше вважався рядком, а насправді може бути `undefined`, і компілятор це
побачив. Тепер скрізь явний запасний варіант:

```ts
const lines = payload.commit.message.split('\n');
const title = lines[0] ?? '';
```

## 6. Типи предметної області

Описані в `src/types/`:

**`commit.ts`** — `Commit` (вигляд, у якому коміт використовує інтерфейс),
`GitHubCommitPayload` (лише ті поля відповіді, які проєкт справді читає) і
`CommitType`. Останній зібрано зі списку відомих типів:

```ts
export const KNOWN_COMMIT_TYPES = ['feat', 'fix', 'docs', ...] as const;
export type KnownCommitType = (typeof KNOWN_COMMIT_TYPES)[number];
export type CommitType = KnownCommitType | typeof OTHER_COMMIT_TYPE;
```

Запис `as const` робить масив незмінним і перетворює його елементи на
літеральні типи, а `[number]` збирає з них обʼєднання. Так список існує в
одному місці: він і перевіряється компілятором, і використовується під час
виконання.

**`state.ts`** — розмічене обʼєднання станів списку:

```ts
export type CommitListState =
    | { readonly status: 'loading' }
    | { readonly status: 'error'; readonly message: string }
    | { readonly status: 'ready'; readonly commits: readonly Commit[] };
```

Це найкорисніша заміна в усій роботі. Раніше стан описували три незалежні
прапорці, і код міг випадково показати одночасно завантаження й помилку.
Тепер неможливий стан просто не описується, а перевірка `status` звужує тип:
до `message` можна звернутися лише в гілці помилки, компілятор не дозволить
інакше.

## 7. Типи зникають під час збірки

Головне, що довелося врахувати: `interface GitHubCommitPayload` не існує в
браузері. Якби код просто написав `const data = await response.json() as
GitHubCommitPayload[]`, це була б обіцянка компіляторові, яку ніхто не
перевіряв: при зміні формату відповіді сторінка впала б пізніше й у чужому
місці.

Тому `json()` повертає `unknown`, а дані проходять перевірку в середовищі
виконання:

```ts
const data: unknown = await response.json();
const payloads = data.filter(isGitHubCommitPayload);
```

Функція `isGitHubCommitPayload` оголошена як `value is GitHubCommitPayload` —
це захисник типу: після неї компілятор знає тип, а перевірка справді
відбулася.

Та сама логіка в `dom.ts`: замість `querySelector(...)!` є функція
`requireElement`, яка кидає помилку з назвою селектора. Знак оклику прибирає
скаргу компілятора, але не додає перевірки; функція додає обидва.

## 8. ESLint і Prettier

ESLint налаштований плоским конфігом із наборами
`recommendedTypeChecked` і `stylisticTypeChecked` — правилами, що спираються на
типи. Вони ловлять те, чого не видно з самого тексту: забутий `await`,
порівняння непорівнюваних значень, зайве приведення типів.

Обовʼязки розділені: ESLint відповідає за помилки, Prettier — за вигляд коду.
Конфлікти між ними знімає `eslint-config-prettier`, який іде останнім і
вимикає в ESLint усі правила форматування.

У налаштуваннях Prettier два винятки:

- HTML і CSS лишаються з подвійними лапками, бо одинарні лапки в селекторі
  `[data-theme='dark']` виглядають незвично, хоча й допустимі;
- YAML форматується двома пробілами, бо так прийнято у файлах GitHub Actions.

Каталог `docs/` внесений до `.prettierignore`: звіти — це суцільний текст із
таблицями, і автоматичне перенесення рядків робить їх менш читними.

## 9. Публікація через GitHub Actions

Раніше Pages віддавав файли просто з гілки. Тепер у мережу має потрапляти
вміст `dist/`, якого в репозиторії немає й не повинно бути — зібрані файли це
похідний продукт, і тримати їх у системі контролю версій означало б отримувати
конфлікти при кожному злитті.

Workflow `.github/workflows/deploy.yml` на кожен запис у `main`:

1. ставить залежності через `npm ci` — рівно ті версії, що в `package-lock.json`;
2. перевіряє типи;
3. запускає ESLint;
4. перевіряє форматування Prettier;
5. збирає проєкт;
6. публікує `dist/` на GitHub Pages.

Перевірки стоять **до** збірки свідомо: якщо код не проходить контроль якості,
публікувати його не треба. Усі шість кроків прогнав локально перед комітом —
проходять.

У налаштуваннях репозиторію джерело публікації довелося перемкнути з «Deploy
from a branch» на «GitHub Actions».

## 10. Перевірка валідатором розмітки

Перевірено і вихідні сторінки, і те, що насправді публікується — вміст
`dist/`. Помилок і попереджень немає в жодній із восьми перевірок.

Валідатор видав лише зауваження рівня info: Prettier закриває порожні теги
слешем (`<meta ... />`), і валідатор нагадує, що в HTML цей слеш нічого не
означає. Розмітка від цього не стає недійсною, а вимкнути таке форматування
Prettier не дозволяє, тому лишив як є.

## 11. Відомі обмеження

**Попередження npm audit.** `npm audit` показує дванадцять зауважень рівня
moderate. Усі вони тягнуться з однієї транзитивної залежності `minimatch`
усередині інструментів розробки й стосуються лише складання проєкту — у
браузер цей код не потрапляє. Оновлення, яке їх закриває, вимагає старших
версій ESLint, тому лишив як є й зафіксував тут.

**Дублювання розмітки.** Шапка, бічна панель і підвал далі повторюються в
чотирьох файлах. Vite сам по собі шаблонізації не дає: для цього потрібен
окремий плагін або перехід на фреймворк.

**Перевірка відповіді неповна.** `isGitHubCommitPayload` перевіряє наявність і
тип ключових полів, але не кожне вкладене поле. Повну перевірку зручніше
робити бібліотекою схем, і це окреме рішення, яке тягне ще одну залежність.

2. `chore: configure typescript in strict mode`
3. `refactor: describe domain types for commits and theme`
4. `refactor: port client modules to typescript`
5. `chore: add eslint and prettier`
6. `ci: build and publish the site with github actions`
7. `docs: add report for lab work 6`

## 13. Висновки

Проєкт перейшов від набору файлів, які віддавалися як є, до проєкту зі
збіркою й автоматичними перевірками. TypeScript у строгому режимі знайшов
місця, де код мовчки покладався на вдалий збіг: звернення за індексом і дані з
мережі, яким просто вірили. Найкориснішою виявилася не сама типізація кожної
змінної, а розмічене обʼєднання станів — воно прибрало цілий клас помилок,
зробивши неможливі стани такими, які неможливо описати. Контроль якості
перенесено з «не забути запустити» в CI, де він виконується на кожен запис у
головну гілку.
